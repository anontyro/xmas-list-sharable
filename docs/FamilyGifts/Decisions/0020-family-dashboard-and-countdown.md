# 0020 · The family page shows counts, a countdown, the guest's planner and earlier years from data that carries no claim information

**Status:** Agreed · **Work items:** FG-505 · **Spec:** `Docs/FamilyGifts/Specs/2026-11-17-FG-002-sticker-book-design.md` D64, D65, D66, D67, D68, D69, D70, D71

The family page and the list page are rebuilt from the Sticker Book pieces. Everything they show about other people's gifts is public (names, counts, prices, notes); claims stay behind the guest's own session.

- **Member picture (D64).** `member.avatar` is a nullable text column (migration `0001_member_avatar.sql`). The allowed values are the eight names in `AVATAR_STICKERS` (`gingerbread, reindeer, star, holly, child, santahat, snowflake, snowglobe`), checked in code by a zod schema, not by a database constraint, so the list can change without a migration. `toAvatar` turns null or a name no longer allowed into null, and the UI then shows the member's initial. Nothing writes the column yet; the admin screen does in R6c.
- **Dashboard data (D65).** `getFamilyDashboard()` returns, per member, `avatar`, and per list, `giftCount` (gifts not deleted; a list with none counts 0). It still returns only active members' open lists. `getEarlierYears()` returns archived lists of active members grouped by occasion and year, newest year first, each with member id, name, picture and gift count. Neither carries any claim, interest, guest, planner, recovery, token or hash key or value; the projection-isolation test checks both.
- **Countdown (D66).** `daysUntilChristmas(now)` counts whole days from today's Europe/London calendar date to the coming 25 December: `0` on the day, `null` from 26 December. It compares calendar dates, so the March and October clock changes never shift the count. The hero shows "N days" (or "Today!") with the calendar sticker only when a Christmas list of the current year exists and the count is not null. The "current year" comes from the server clock, so it can be a few hours off London time on 1 January; the count is `null` then anyway.
- **Planner card (D67).** A guest with a name sees the yellow card on the family page and in the list page sidebar: "£X left to plan of £Y" with a total budget, "£Y over your £Z budget" when over it (added; the spec had no case for this), "£X planned so far" without a budget, and "Start planning" when nothing is planned. `getPlannerSummary()` takes planned, spent and the budget from `getPlanner()`, so the card and the planner page cannot disagree. It reads the planner's default period, the newest one the guest has entries in. Visitors without a name see no card.
- **Earlier years (D68).** A sky "Earlier years" ribbon and one card per archived occasion and year ("Christmas 2025", pill "Archived · read-only", "View lists") appear only when archived lists exist. They link to `/earlier/<year>`, a read-only page of that year's archived lists as member cards (the lists themselves show the archived notice and no claim buttons). A year with no archived lists, or one that is not a number, shows "We couldn't find that year".
- **List page (D69).** Hero (back button "< Family", "Sarah's Christmas", "2026 · 3 gifts · shared list", tree sticker), then gifts under ribbons "★ MOST WANTED" (red), "WOULD LOVE" (green) and "NICE TO HAVE" (sky) in the owner's order, each gift a `GiftRow`. The ribbons are level 2 headings and gift titles level 3. Only the priority sort has ribbons: another sort is a flat list, because groups would break the sort. The sidebar holds the filters (wide screens), the planner card and Copy link; on phones it comes last. The archived notice and the name note stay.
- **Sort and filter (D70).** The same URL parameters and the same pure functions as before, so old links work. Wide screens show buttons for Sort by, Priority (All and the three), an "Up to £N" slider from £0 to the dearest gift rounded up to £5 (at the top it reads "Any price" and `max` is left out of the URL) and Availability. Phones show a chip row (Sort: …, Available only, Under £25, More filters) and a dialog with the same controls that traps focus and closes on Escape. Every control is a button with `aria-pressed` or a slider with a label, so state is in text as well as colour. `min` is still read from the URL but has no control.
- **Status wording (D71).** Pills keep the words from `statusLabel`: Available, Interested, Reserved by you, Purchased by you, Reserved by Sam, Purchased by Sam, toned white, pink, yellow, mint. Claim buttons use the theme: Interested pink, Reserve red, Mark purchased mint, the rest dashed ghost buttons. Labels, `aria-label`s and behaviour did not change.

## Why

The family page is where people choose whose list to open, so counts and a countdown tell them where to look without opening each list. The planner card keeps the guest's own money plan one tap away but is computed from the planner's own totals so the two never disagree. The filter controls are plain buttons and one slider so they work at 375 px with a thumb and with a keyboard.

## Consequences

- A member with two open lists gets two cards, labelled "Open Sarah's <list title> list".
- `PriorityChip` stays until the owner editor replaces `OwnerItemList` (R6a).
- Two gifts created in the same millisecond tie on `createdAt` and then on a random id; the e2e helper gives each gift a later time to avoid that in tests.
- There is no e2e test of the countdown (it depends on the date); the unit test covers the dates.
